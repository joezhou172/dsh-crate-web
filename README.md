# DSH Crate

DSH Crate 把 DeepSeek Harness 的一套 Profile 配置导出为 `.dshcrate`，方便迁移、分享和日后恢复。收到包的人可以先看内容、检查依赖与风险，再恢复到新的 Profile。

它是第三方社区项目。目前提供 **Preview** 版本，兼容范围以实际测试的组合为准。

本轮发布候选为 **`0.1.2-preview.7`**，使用 `preview` 通道。迁移测试请固定安装此版本；发布状态以 npm 实际查询结果为准。

## 安装与开始使用

通过 DSH 自带的插件命令安装。下面以 `web` 为例，请换成你实际使用的 Profile 名称：

```powershell
dsh plugin --profile web add dsh-crate-web@0.1.2-preview.7
```

重启 DSH，进入 **Settings → DSH Crate**。Windows x64 包内带有 Python 3.14.6，无需另装系统 Python。离线安装可以使用同版本 tgz，但恢复时是否还需联网，取决于包内有没有包含所需插件制品。

插件需要安装到目标 DSH Profile。全局安装 npm 包不能替代这一步；DSH 模块和 React 由宿主提供，Crate 不会为一个空目录自动装上另一套 DSH。

## Preview.7 的迁移功能

- 导出前生成实际包并显示体积；新界面使用有效期 15 分钟的冻结计划，最终下载同一文件。修改选项后需重新预览。
- 独立插件选择页与运行插件页，支持搜索、选择状态和来源筛选；选择只影响导出包。
- 选择已安装内容或公共 npm 的精确版本；可以把插件加入包而不安装到当前环境。
- 内嵌与仅引用两种导出方式；仅引用需要明确确认，恢复仍依赖制品来源。
- 快速模式使用 ZSTD 9，紧实模式使用 ZSTD 19。新导出使用 schema 4；仍可读取旧 schema 1–3，旧版 Crate 不保证能读取 schema 4，请先升级接收端。
- 界面跟随 DSH 的中文/英文和官方深浅色；完整错误放入可复制诊断弹窗。
- 修复 Windows npm 打包时，过长包目录作为工作目录引发的 WinError 267。

本机真实测试覆盖 DSH 0.2.1-rc.5、Node 24.21.0：两档导出/恢复、重启、核心文件/搜索/PowerShell 工具和部分插件本地数据能力。完整模型业务与 Win10 目标机器尚未验收。`@howmp/dsh-pentest@0.1.0-rc.34` 的渗透预设因旧 `persona` 配置加载失败，是已知第三方兼容问题；打包恢复成功不等于该插件功能兼容。

## 一次迁移会经过哪些步骤

1. **导出（Export）**：选择源 Profile，记录配置、插件身份、来源和环境信息。插件制品可以嵌入包内，也可以只保留引用。
2. **检查（Inspect / Preflight）**：核对格式、完整性、依赖和环境差异。`BLOCKER` 会阻止导入，`WARNING` 会保留在结果中。
3. **恢复（Import）**：默认创建新的 Profile。原 Profile 保留；覆盖、删除、切换已有 Profile 都需要单独确认。
4. **验证（Verify）**：在隔离环境中检查恢复后的组合。启动成功和模型、工具、插件真正能用，是不同的检查项。

只引用插件的包通常更小，但恢复时需要相应的下载来源或本地制品。嵌入插件可以减少对来源的依赖；整个环境能否离线恢复，还要把宿主和其他依赖一起核实。

凭据值不在导出范围内。`requiredSecrets` 只记录需要哪些 Secret，不保存它们的值。分享前仍应查看包的清单和配置内容。诊断页面保留失败阶段、原始错误和可复制 JSON，便于定位问题。

## Verify 的结果怎么看

默认 Verify 会启动独立验证桌面，隔离 DSH Home、工作区、用户数据、TEMP 和缓存，不调用模型。它能检查的启动、页面、会话动作与清理，会分别记录结果。

模型响应、原生工具和插件核心功能需要专门的真实测试。默认 Verify 不会把这些未执行的项目算作通过。

| 状态 | 含义 |
| --- | --- |
| `PASS` | 这一项实际执行并通过 |
| `FAIL` | 这一项实际执行但失败 |
| `UNTESTED` | 没有执行，或证据不足以给出通过结论 |
| `DEGRADED` | 可以使用，但存在已说明的非阻塞问题 |

官方新会话动作可能复用已有的空白会话，因此“点击后 ID 没变”本身不能证明创建失败。需要结合实际调用和页面状态判断。

## Windows 终端修复怎么用

`preview.6` 随包提供了[独立桌面构建入口](./packaging/windows-terminal/README.md)。它针对已锁定的 **DSH 0.2.1-rc.5 / Windows x64 / 随包 Node 24.21.0** 制品，处理 runner 空 stdin 导致的退出 127，以及退出码、就绪和关闭事件的传播问题。

使用时显式创建一个新的桌面副本：

```powershell
# <包目录> 是已经安装的 dsh-crate-web 目录。
& "<包目录>\runtime\python\python.exe" "<包目录>\packaging\windows-terminal\build.py" --source "<匹配的官方桌面目录>" --destination "<不存在的新副本目录>"
```

构建会核对输入 EXE、ASAR 和控制台 Node 的哈希。同样写着 rc.5 的其他制品，不一定匹配。原安装保持不变；脚本也不会自动启动新副本。

这个入口不随插件安装自动执行，不包含完整官方桌面或历史 Inspector／NARB 补丁。新副本仍启用完整性检查，但改写后的 EXE 不再保留原代码签名的有效性。具体输入身份、限制和验收方法见随包说明。

## 目前验证到哪里了

下面几类证据分别对应不同范围，不能合并成“全部业务通过”。

| 检查范围 | 已有结果 | 适用边界 |
| --- | --- | --- |
| `preview.6` 的发布与干净安装 | `PASS` | 从 npm 下载后普通安装；插件入口可导入，随包构建资源和补丁哈希正确 |
| npm 制品身份 | `PASS` | 本地检查包、CI 发布包和 registry 下载包的 SHA-256 一致 |
| Windows 终端定向验收 | `PASS` | 前轮同字节补丁的独立桌面；恢复后、重启后、移除 Crate 后真实调用终端，正常关闭并释放受控进程及相关 TCP 端口 |
| 默认零模型 Verify | 部分步骤 `PASS`，总结果 `UNTESTED` | 已有组合、启动、页面、新会话动作和清理证据；模型及插件业务步骤未执行 |
| 当前发行组合的完整桌面业务验收 | `UNTESTED` | 还需在同一最终组合中补齐模型、原生工具、各插件及重启、移除链路 |
| 其他操作系统及未锁定的 DSH 制品 | `UNTESTED` | 本轮没有完成对应桌面验收 |

发布流程使用 GitHub Actions 和 npm Trusted Publisher。它先扫描提交及最终 tgz，再普通安装该 tgz，最后发布同一个制品。本轮[发布运行](https://github.com/joezhou172/dsh-crate-web/actions/runs/41200557074)已完成；完整回归为 45 项通过、1 项因未提供专用 runtime 而跳过。

## 已知问题

- **Windows 导入偶发 `WinError 5`**：发生在临时 Profile 改为正式目录名时。界面保留原始错误和回滚结果；具体占用者或权限条件还未锁定。提示“可能被占用”不代表已经确认根因。
- **Inspector 首启耗时仍需定位**：耗时的完整归因与历史 Worker 取消故障是两项待闭合工作，不能因为终端修复通过就认定它们已解决。
- **完整业务验收仍有空缺**：本次 npm 发布没有调用模型，也没有重新启动桌面。定向终端证据不覆盖所有插件功能；逐名称管道释放也没有独立探测。

后续优先补齐当前交付组合的验收，再处理导入失败和 Inspector 的剩余诊断。减小环境包的工作会先考虑可精确下载的制品，同时保留版本、来源和完整性校验。详见[开发计划](https://github.com/joezhou172/dsh-crate-web/blob/main/DEVELOPMENT.md)。

报告问题时，请说明 Crate、DSH、操作系统版本、发生在哪一步，并附去除凭据后的完整诊断。不要提交 API Key、Token、Cookie 或个人 Home。
